# ADR-0009: Mobile release configuration (Android release 1 first)

- **Status:** Accepted
- **Date:** 2026-11-23
- **Deciders:** Founders (Android first for release 1) and engineering (configuration design)

## Context

Master §2 requires Android and iOS builds from **one** shared Expo codebase, with separate release configurations and no forked business logic. The founders decided that **release 1 targets Android**. iOS stays buildable from Phase 1, and its store release follows Android.

Several values can't change after the first store upload and are founder decisions: the Android application ID, the iOS bundle identifier, the display name and brand assets. Their real values are not yet approved.

## Decision

### One `app.config.ts`, environment-driven

`APP_VARIANT` (`development` | `preview` | `production`) selects:

| Variant     | Name suffix  | ID suffix  | Scheme suffix | Distribution                                    |
| ----------- | ------------ | ---------- | ------------- | ----------------------------------------------- |
| development | ` (Dev)`     | `.dev`     | `-dev`        | Internal dev-client build (APK / iOS simulator) |
| preview     | ` (Preview)` | `.preview` | `-preview`    | Internal testing build                          |
| production  | none         | none       | none          | Store                                           |

- **Identifiers** come from `ANDROID_APPLICATION_ID` and `IOS_BUNDLE_IDENTIFIER`.
  - development and preview fall back to the reserved placeholder `com.example.samkrushi`, which can never be published.
  - **production fails to resolve** without real values, so a placeholder can't reach a store by accident.
- **Display name and scheme** come from `APP_DISPLAY_NAME` and `APP_SCHEME`. Defaults are `SAMKRUSHI` and `samkrushi`, pending brand approval.
- Variants get distinct IDs, so dev, preview and production builds install side by side on one device.

### Android (release 1)

- `permissions: []` plus an explicit `blockedPermissions` list. After prebuild the merged manifest requests only `INTERNET` and `VIBRATE`. Location, contacts, audio, overlay and legacy storage are removed.
- Each future permission (e.g. `POST_NOTIFICATIONS` in Phase 9) must be added deliberately and reflected in the Play Data safety form.
- Adaptive icon and splash use **placeholder** assets until brand assets are approved.
- EAS profiles:
  - `development`: dev client, APK;
  - `preview`: internal APK;
  - `production`: `app-bundle` (AAB), `autoIncrement`.
- Submit profile `production.android`: Play track `internal`, `releaseStatus: draft`. A staged rollout is promoted manually in Play Console after internal testing.
- The Play service-account key is supplied as an EAS secret, never committed.
- Signing uses an EAS-managed upload keystore plus Play App Signing; keystores are never committed (`.gitignore` blocks `*.jks`, `*.keystore`).
- Build numbers: `cli.appVersionSource: remote`. EAS owns `versionCode` and `buildNumber`, so `version` in `app.config.ts` is the marketing version only.

### iOS (maintained, released after Android)

- `ios.bundleIdentifier` is resolved the same way; `supportsTablet: false` (iPhone only) as the development default.
- EAS profiles exist for every variant: development is a simulator build; preview and production need Apple credentials.
- **No iOS submit profile yet.** It's added once the Apple Developer account, App Store Connect app ID and bundle ID are approved.
- These are still to do before the iOS store release:
  - privacy manifest;
  - App Privacy disclosures;
  - export-compliance answer;
  - associated domains (Universal Links);
  - APNs key.
- They're tracked in `docs/business-decisions.md` and must not be guessed.

### Shared logic, platform-only differences

- All screens, state, API calls and business rules live in `apps/mobile/src` and are shared.
- Platform-specific code is limited to native behaviour (Android Back handling, iOS swipe-back, notification channels, permission prompts), via `Platform.select` or `*.android.tsx` / `*.ios.tsx` files, never via forked business logic.
- Native projects (`android/`, `ios/`) are generated by Expo prebuild and not committed. Native changes go through config plugins.

### Payments (see ADR-0008)

Release 1 uses Razorpay Hosted/Standard Checkout through `expo-web-browser`, so no native payment SDK is required. The dev-client setup keeps a later native SDK possible without changing the build architecture.

## Consequences

- CI checks that development and preview configs resolve and that the Android Hermes bundle builds. Cloud builds (`eas build`) need an Expo account and EAS project ID: **founder/account decision**.
- Releasing iOS later needs only identifiers, credentials, an iOS submit profile and the iOS-specific privacy work above. The app code doesn't change.
- Changing the production identifiers after the first upload is impossible, so `ANDROID_APPLICATION_ID` must be confirmed before the first `production` build.
